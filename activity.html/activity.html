Part 0: Background and Setup

What is a Data Warehouse?

A data warehouse is a centralized repository designed for analytical queries across large volumes of historical data. Unlike transactional databases (OLTP), which are optimized for recording individual events quickly, a data warehouse (OLAP) is structured for aggregation, trend analysis, and business reporting.

Characteristic OLTP (Transactional) OLAP (Analytical)
PurposeRecord daily transactionsAnalyze historical data
Query typeSimple reads/writesComplex aggregations
Data modelNormalized (3NF)Denormalized (Star/Snowflake)
Optimized forWrite throughputRead/query performance
UsersApplication backendAnalysts, managers
Update frequencyReal-timeBatch (daily/weekly)
HistoryCurrent stateYears of history

The Kimball Dimensional Modeling Methodology

Ralph Kimball's dimensional modeling approach is the most widely adopted framework for designing data warehouses. Data is organized into two types of tables:

  • Fact tables — record measurements of business events (e.g., a sale, a payment). Rows are numerous; columns are mostly numeric measures and foreign keys to dimensions.
  • Dimension tables — provide the context surrounding each event (e.g., which customer, which product, when). Rows are fewer; columns are descriptive attributes used for filtering and grouping.

Together they form a star schema — the fact table at the center, dimension tables radiating outward.

The Kimball 4-Step Process

For every business process you want to model, apply these four steps in order:

  1. Select the business process — What event or process are we measuring?
  2. Declare the grain — What does exactly one row in the fact table represent? Be as specific as possible.
  3. Identify dimensions — What context surrounds each event? Think: who, what, where, when.
  4. Identify facts — What numeric measures capture the event? These are the columns analysts will SUM(), AVG(), etc.

Business Process 2: Customer Payments

Scenario. The finance team needs to track revenue received (not just ordered). They want to know which months had the highest cash inflow, and which customers pay most regularly.

Guided Questions — Business Process 2: Customer Payments
  1. Examine the payments table: (customerNumber, checkNumber, paymentDate, amount). What real-world event does each row represent? Is this the same event as an order line? Why does it deserve its own separate fact table?
  2. The finance analyst asks: "Which month in 2004 had the highest total payment received?" At what grain should the fact table operate to answer this?
  3. What contextual dimensions would help analyze payments? Note that payments has no direct link to employees or products — is that a problem?
  4. The payments table has only one numeric column: amount. Is one measure enough for a useful fact table?

Part 2: Introduction to dbt

Now that you have designed the dimensional model, you will implement it using dbt (data build tool) — the industry-standard tool for the Transform step in modern ELT pipelines.

What is dbt?

ELT vs. ETL

Traditional ETL pipelines Extract from sources, Transform outside the warehouse, then Load. Modern ELT pipelines Extract and Load raw data first, then Transform it inside the warehouse using SQL.

dbt handles the T in ELT. It takes raw tables already in your database and transforms them into clean, modelled tables — all using plain SQL SELECT statements. dbt is not responsible for extraction. In this lab, load_source.py handles that.

Key Concepts

ConceptExplanation
Model A .sql file containing a SELECT statement. dbt materialises it as a view or table. One file = one model.
ref() References another dbt model: {{ ref('stg_orders') }}. dbt resolves the correct schema and determines build order.
Source A raw table not managed by dbt. Declared in sources.yml and referenced with {{ source('classicmodels', 'orders') }}.
Materialization How dbt stores a model. view = SQL view (no data stored), table = physical table rebuilt on each dbt run.
DAG Directed Acyclic Graph. dbt builds this automatically from your ref() calls and executes models in the correct order.

Three-Layer Architecture

We structure all models in three layers. Each layer has one responsibility:

Source Layer
main.*  —  Raw tables loaded by load_source.py
↓
Staging Layer
stg_* (views)  —  Rename columns, cast types — no business logic
↓
Dimension Layer
dim_* (tables)  —  Conformed dimensions with surrogate keys
↓
Mart Layer
fct_* (tables)  —  Fact tables joining dimensions with numeric measures

Project Structure

classicmodels_dw/
  dbt_project.yml      # project name, profile, materialization settings
  profiles.yml         # DuckDB connection (path to .duckdb file)
  load_source.py       # converts MySQL dump to DuckDB
  models/
    sources.yml        # declares the 8 raw source tables
    staging/           # stg_* views  (one per source table)
    dimensions/        # dim_* tables (5 conformed dimensions)

Step 3: Build the Dimension Models

dbt run --profiles-dir . --select dimensions

dim_date — Generated Date Dimension

Unlike every other dimension, dim_date has no source table — it is generated using DuckDB's generate_series.

models/dimensions/dim_date.sql
with date_spine as (
    -- Date range covers all ClassicModels order dates.
    -- Extended to full calendar years for clean reporting.
    select generate_series::date as date_day
    from generate_series(
        date '2003-01-01',
        date '2006-12-31',
        interval '1 day'
    )
)
select
    date_day                                as date_id,
    date_day                                as full_date,
    extract('year'    from date_day)::int   as year,
    extract('quarter' from date_day)::int   as quarter,
    extract('month'   from date_day)::int   as month,
    strftime('%B', date_day)                as month_name,
    extract('week'    from date_day)::int   as week_of_year,
    extract('day'     from date_day)::int   as day_of_month,
    extract('dow'     from date_day)::int   as day_of_week,
    strftime('%A', date_day)                as day_name,
    (extract('dow' from date_day) in (0, 6)) as is_weekend
from date_spine

dim_product — Joining Across Staging Models

dim_product enriches products with their line descriptions by joining two staging models. The ref() calls ensure stg_productlines is built before dim_product.

models/dimensions/dim_product.sql
select
    row_number() over (order by p.product_code)   as product_key,
    p.product_code,
    p.product_name,
    p.product_line,
    pl.text_description                           as product_line_description,
    p.product_scale,
    p.product_vendor,
    p.buy_price,
    p.msrp
from {{ ref('stg_products') }} p
left join {{ ref('stg_productlines') }} pl
    on p.product_line = pl.product_line
Surrogate Keys

row_number() over (order by product_code) generates a surrogate key — an integer that uniquely identifies each dimension row, independent of the source system's natural key (product_code). Fact tables reference dimension rows via these integer keys.

dim_employee — Self-Join for Hierarchy

The employees table is self-referential (reportsTo). We resolve the manager's name with a self-join on the staging model.

models/dimensions/dim_employee.sql
select
    row_number() over (order by e.employee_id)       as employee_key,
    e.employee_id,
    e.first_name,
    e.last_name,
    e.first_name || ' ' || e.last_name               as full_name,
    e.job_title,
    e.email,
    e.office_code,
    e.reports_to_employee_id,
    mgr.first_name || ' ' || mgr.last_name           as manager_full_name
from {{ ref('stg_employees') }} e
left join {{ ref('stg_employees') }} mgr
    on e.reports_to_employee_id = mgr.employee_id

Step 4: Build the Fact Tables

dbt run --profiles-dir . --select marts

fct_order_lines — The Core Sales Fact

Every order line item becomes one row. We join to dimension tables using the surrogate keys established in the previous step.

models/marts/fct_order_lines.sql
select
    od.order_id,
    od.order_line_number,
    o.order_date                           as order_date_id,
    dc.customer_key,
    dp.product_key,
    de.employee_key                        as sales_rep_key,
    dof.office_key,
    od.quantity_ordered,
    od.price_each,
    round(od.quantity_ordered * od.price_each, 2)  as revenue,
    dp.buy_price,
    round(od.quantity_ordered * dp.buy_price, 2)   as cost,
    round(
        (od.quantity_ordered * od.price_each)
      - (od.quantity_ordered * dp.buy_price), 2
    )                                      as gross_profit
from {{ ref('stg_orderdetails') }} od
join {{ ref('stg_orders') }} o
    on od.order_id = o.order_id
join {{ ref('dim_customer') }} dc
    on o.customer_id = dc.customer_id
join {{ ref('dim_product') }} dp
    on od.product_code = dp.product_code
left join {{ ref('dim_employee') }} de
    on dc.sales_rep_employee_id = de.employee_id
left join {{ ref('dim_office') }} dof
    on de.office_code = dof.office_code

Why LEFT JOIN for employee and office? Some customers have no assigned sales representative (sales_rep_employee_id IS NULL). Using LEFT JOIN preserves those order lines instead of silently dropping them. Note that buy_price is denormalized from dim_product into the fact table so margin calculations can be done in a single scan, without requiring an additional join at query time.

fct_payments — The Payment Fact

A narrower fact: two dimensions, one measure. check_number is kept as a degenerate dimension (no separate dimension table, but useful for tracing individual payments).

models/marts/fct_payments.sql
select
    p.check_number,
    p.payment_date               as payment_date_id,
    dc.customer_key,
    p.amount
from {{ ref('stg_payments') }} p
join {{ ref('dim_customer') }} dc
    on p.customer_id = dc.customer_id

fct_sales_performance — Monthly Aggregate Fact

This periodic snapshot uses ref('fct_order_lines') — a fact-on-fact reference, aggregated by rep and calendar month.

models/marts/fct_sales_performance.sql
select
    sales_rep_key,
    office_key,
    date_trunc('month', order_date_id)::date     as month_date,
    extract('year'  from order_date_id)::int     as year,
    extract('month' from order_date_id)::int     as month,
    count(distinct order_id)                     as order_count,
    count(distinct customer_key)                 as unique_customers,
    sum(quantity_ordered)                        as total_units_sold,
    round(sum(revenue), 2)                       as total_revenue,
    round(sum(gross_profit), 2)                  as total_gross_profit,
    round(avg(revenue), 2)                       as avg_order_line_revenue
from {{ ref('fct_order_lines') }}
-- Orders with no assigned sales rep are excluded (rep-level analysis only).
where sales_rep_key is not null
group by 1, 2, 3, 4, 5

Step 5: Explore Your Data Marts

With all three data marts built, run the business queries below. These are the questions that motivated the entire warehouse design.

Revenue by product line with margin
SELECT
    p.product_line,
    SUM(f.revenue)              AS total_revenue,
    SUM(f.gross_profit)         AS total_gross_profit,
    COUNT(DISTINCT f.order_id)  AS order_count,
    ROUND(SUM(f.gross_profit) /
          NULLIF(SUM(f.revenue),0) * 100, 1) AS gross_margin_pct
FROM   fct_order_lines f
JOIN   dim_product p ON f.product_key = p.product_key
GROUP  BY p.product_line
ORDER  BY total_revenue DESC;
Top 5 customers by total payments received
SELECT
    c.customer_name,
    c.country,
    SUM(fp.amount)   AS total_paid,
    COUNT(*)         AS payment_count
FROM   fct_payments fp
JOIN   dim_customer c ON fp.customer_key = c.customer_key
GROUP  BY c.customer_name, c.country
ORDER  BY total_paid DESC
LIMIT  5;
Top sales reps in 2004
SELECT
    e.full_name,
    e.job_title,
    o.territory,
    SUM(sp.total_revenue)    AS ytd_revenue,
    SUM(sp.order_count)      AS total_orders,
    SUM(sp.unique_customers) AS customers_served
FROM   fct_sales_performance sp
JOIN   dim_employee e ON sp.sales_rep_key = e.employee_key
JOIN   dim_office   o ON sp.office_key    = o.office_key
WHERE  sp.year = 2004
GROUP  BY e.full_name, e.job_title, o.territory
ORDER  BY ytd_revenue DESC
LIMIT  5;
Monthly revenue trend
SELECT
    dd.year,
    dd.month,
    dd.month_name,
    SUM(f.revenue)  AS monthly_revenue
FROM   fct_order_lines f
JOIN   dim_date dd ON f.order_date_id = dd.date_id
GROUP  BY dd.year, dd.month, dd.month_name
ORDER  BY dd.year, dd.month;
Checkpoint

Verify your results:

  1. Classic Cars has the highest revenue among all product lines.
  2. Total revenue across all time is approximately $9.6 million.
  3. At least one top-5 sales rep in 2004 is from the EMEA or APAC territory.
  4. Monthly revenue shows seasonal variation with peaks in late 2003 and 2004.
